## 1. В чём главное отличие виртуальной машины от Docker-контейнера?

Виртуальная машина эмулирует полноценный компьютер: у неё есть собственная
гостевая операционная система, ядро и выделенные виртуальные ресурсы. Docker-контейнер
изолирует процесс и его файловую систему, но использует ядро операционной системы
хоста. Поэтому контейнер обычно запускается быстрее и занимает меньше места, а
виртуальная машина даёт более сильную изоляцию и может запускать другую ОС.

## 2. Зачем нужен файл `.dockerignore` и к чему приведёт его отсутствие?

`.dockerignore` исключает из build context файлы, которые не нужны внутри образа:
`.env`, `node_modules`, тесты, логи, документацию, артефакты сборки и каталоги IDE.
Без него Docker будет отправлять лишние данные демону, сборка станет медленнее,
образ может увеличиться, а секреты или локальные файлы случайно попадут в слои
образа. В этой лабораторной `.env` исключён и дополнительно не копируется в финальный
образ.

## 3. Что такое multi-stage build и какие преимущества он даёт?

Multi-stage build разделяет Dockerfile на несколько этапов. В этапе `builder`
устанавливаются TypeScript и остальные инструменты разработки, после чего исходный
код компилируется в `dist`. В финальный этап копируются только скомпилированные
файлы и production-зависимости. Это уменьшает размер образа, сокращает поверхность
атаки и не раскрывает компиляторы, тесты и dev-зависимости в runtime-контейнере.

## 4. Зачем отдельно копировать файлы зависимостей и исходный код?

Docker кэширует каждый слой. Если сначала скопировать `package.json` и
`package-lock.json`, выполнить `npm ci`, а затем скопировать `src`, изменение
исходного кода не заставит заново скачивать зависимости. Установка повторяется
только после изменения манифестов, поэтому сборка получается быстрее и
воспроизводимее благодаря lock-файлу.

## 5. Чем отличаются `EXPOSE` в Dockerfile и `-p` у `docker run`?

`EXPOSE 8080` документирует порт, который приложение слушает внутри контейнера;
сам по себе этот оператор не открывает порт на компьютере. Флаг `-p 8080:8080`
создаёт проброс с порта хоста на порт контейнера. Поэтому endpoint доступен с
хоста только после запуска контейнера с `-p`.
