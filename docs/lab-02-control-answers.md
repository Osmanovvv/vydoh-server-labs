## 1. Query, Path и Request Body

**Query-параметры** передают параметры выборки и фильтрации после знака `?`:
`GET /users?page=2&page_size=20&blocked=false`. Они подходят для необязательных
фильтров, сортировки, поиска и пагинации. Их изменение обычно не меняет сам ресурс.

**Path-параметры** являются частью адреса конкретного ресурса:
`GET /items/7d2b8c7a-4d75-4e5b-9c77-4d0d5b4e5d18`. Они нужны, когда без значения
идентификатора невозможно определить ресурс. В OpenAPI такой параметр всегда
описывается как `in: path` и `required: true`.

**Request Body** содержит данные, которые создают или изменяют ресурс, обычно в
формате JSON. Например, `POST /users/{userId}/items` получает `text`, `priority`,
`topic_id` и срок записи в `ItemCreateRequest`. Большие или структурированные
данные нельзя помещать в URI: body удобнее валидировать по схеме и не ограничивает
длину адреса.

В спецификации «ВЫДОХ» query используется для фильтров и страниц списков,
path — для UUID пользователя, записи, сферы или напоминания, а body — для входных
данных входа, создания и частичного обновления.

## 2. Идемпотентность HTTP-методов

Метод идемпотентен, если повторение одного и того же запроса приводит к тому же
состоянию ресурса, что и однократное выполнение. Ответы и журналы при повторах могут
отличаться, но итоговое состояние ресурса не должно дополнительно изменяться.

- `GET` только читает данные, поэтому повторный запрос не меняет ресурс.
- `PUT` полностью заменяет ресурс заданным представлением. Повторная отправка того
  же представления оставляет ресурс в том же состоянии.
- `DELETE` повторно подтверждает отсутствие ресурса. Первый запрос может вернуть
  `204`, а повторный — `404`, но состояние остаётся удалённым или неактивным.
- `POST` обычно создаёт новый ресурс. Повторная отправка может создать второй
  ресурс, поэтому метод не считается идемпотентным. Для платежей и webhook в
  «ВЫДОХ» повторная обработка отдельно защищается уникальными ключами БД.

В API лабораторной `DELETE /items/{itemId}` и `DELETE /topics/{topicId}` выполняют
логическое удаление или архивацию, поэтому повторное применение не возвращает
ресурс в активное состояние.

## 3. Разница между 401 Unauthorized и 403 Forbidden

`401 Unauthorized` означает, что сервер не может считать запрос аутентифицированным:
cookie отсутствует, истекла или повреждена, либо неверны логин, пароль или TOTP.
Клиенту нужно выполнить вход заново. В OpenAPI этот код используется для закрытых
операций и для ошибок входа.

`403 Forbidden` означает, что личность уже подтверждена, но у текущей роли нет права
на действие. Например, обычная сессия без административной роли не может открыть
карточку пользователя или изменить запись в админ-панели. Повторный вход с теми же
правами такую ошибку не исправит.

## 4. `components/schemas` и `$ref` в OpenAPI

`components/schemas` — раздел переиспользуемых моделей данных. В спецификации
«ВЫДОХ» там находятся `ItemResponse`, `TopicResponse`, `SettingsResponse`,
`ErrorResponse`, перечисления статусов и схемы входящих запросов.

`$ref` подключает модель по ссылке, например:

```yaml
schema:
  $ref: '#/components/schemas/ErrorResponse'
```

Это устраняет копирование одинаковой структуры, гарантирует единый формат ошибок
во всех операциях и позволяет Swagger UI построить общую документацию. При изменении
схемы достаточно исправить её один раз в `components/schemas`.

## 5. PUT и PATCH

`PUT` предназначен для полной замены ресурса. Клиент отправляет полное актуальное
представление; отсутствующее поле обычно означает его замену значением по умолчанию
или удаление. Повторный одинаковый `PUT` идемпотентен.

`PATCH` предназначен для частичного изменения. Клиент отправляет только поля,
которые нужно изменить, остальные значения сохраняются. В `openapi.yaml`
`PATCH /items/{itemId}` может изменить только статус, срок или приоритет записи, а
`PATCH /users/{userId}/settings` — только один параметр расписания. Для таких
операций в схемах заданы `minProperties: 1`, чтобы пустое изменение было ошибкой.

Если клиенту необходимо полностью заменить ресурс и это поддерживается сервером,
следует использовать `PUT`; для точечной правки данных «ВЫДОХ» подходит `PATCH`.
